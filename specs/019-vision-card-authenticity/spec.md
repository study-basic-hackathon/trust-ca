# 機能仕様: Vision APIによるカード画像コンテンツチェック(PSAなし経路)MVP

**Feature Branch**: `feat/16-vision-authenticity`

**Created**: 2026-08-19

**Status**: Draft

**Input**: Issue #16「Vision APIを使ってカードが本物であるか確認できる機能の調査、MVP実装」

**スコープ境界**: Cloud Vision API(OCR・ラベル検出・オブジェクト位置検出)は画像の「内容」を理解できるが、2枚の画像が同一の物理個体であることまでは保証しない(docs/design/api-catalog.md §5.3)。本MVPは**Vision APIで判定できるレイヤー(内容整合性チェック)のみ**を対象とし、物理的な同一個体照合(画像ハッシュ・特徴点比較等の「自社の画像比較ロジック」)は別タスクとして切り出す。

## User Scenarios & Testing

### User Story 1 - 出品者が四隅画像を登録する (Priority: P1)

PSA鑑定を受けていないカードを出品する販売者は、出品時にカードの四隅等の画像をアップロードし、取引成立後の真贋確認に使う証跡として保存する。

**Why this priority**: 到着後の再撮影と比較する基準画像がなければ、本機能の他のどのステップも成立しない最小価値である。

**Independent Test**: 出品フローで画像をアップロードし、Cloud Storageへ保存されたobject keyとメタデータ(content type、サイズ、SHA-256、撮影種別)がDBに記録されることを確認する。

**Acceptance Scenarios**:

1. **Given** 出品者がPSA証明書番号を持たない、**When** 出品時に四隅等の画像を複数枚アップロードする、**Then** 画像が出品情報に紐付けて保存され、出品時撮影として記録される。
2. **Given** 出品者が画像として不適切なファイル(非画像形式・許容サイズ超過)を送る、**When** アップロードを試みる、**Then** backendは保存前に拒否し、理由を返す。

---

### User Story 2 - 購入者が到着後に画像をアップロードし内容整合性チェックを受け取る (Priority: P2)

購入者は商品到着後、出品時と同一箇所を再撮影してアップロードする。システムはVision APIのOCR・ラベル・領域検出結果を用いて、その画像が「カード撮影として妥当か」「出品時に申告されたカード名・型番等の内容と整合するか」をチェックする。**2枚の画像が物理的に同一の1枚であることの照合は行わない**(スコープ境界を参照)。

**Why this priority**: 出品時画像の保存だけでは価値がなく、到着後の内容チェックまで揃って初めて「申告と異なるカードが届いていないか」という最小限の異常検知価値が生まれる。

**Independent Test**: 出品時に申告されたカード名・型番と、到着後画像をVision APIへ送った際のOCR結果を突合し、`内容整合`または`要確認`のいずれかに正規化されて画面に表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** 出品時に申告されたカード名・型番がある、**When** 購入者が到着後に同一箇所を再撮影してアップロードする、**Then** backendはVision APIのOCR・ラベル・領域検出結果が申告内容と整合するかを評価し、結果を購入者へ表示する。
2. **Given** OCR結果が申告内容と一致しない、カードとして検出できない、Vision APIの解析結果が判断不能、またはAPIエラーである、**When** 内容チェックが完了する、**Then** 自動で「内容整合」にはせず「要確認」として記録し、購入者へその旨と運営者への通報導線を表示する。

---

### User Story 3 - 運営者が要確認ケースを確認する (Priority: P3)

運営者は「要確認」となった内容チェック結果を一覧・詳細で確認し、目視での最終判断につなげる。

**Why this priority**: 自動判定は補助シグナルに過ぎず(docs/design/system-architecture.md §8原則3)、人手確認の入口がなければ「要確認」が宙に浮いてしまう。

**Independent Test**: 「要確認」状態の解析結果を、運営者向けの一覧・詳細取得APIから欠落なく取得できることを確認する。

**Acceptance Scenarios**:

1. **Given** 複数件の解析結果が`内容整合`と`要確認`に分かれて存在する、**When** 運営者が解析結果を照会する、**Then** 出品時申告内容・対象画像・Vision APIの解析要約・正規化結果を確認できる。

---

### Edge Cases

- 出品時に申告されたカード名・型番の情報が存在しない取引に対して、購入者が到着後画像をアップロードしようとした場合、突合対象がないため「要確認」として扱う。
- Vision APIが一時的に利用不能・タイムアウトした場合、再試行のうえ失敗が続けば「要確認」に倒す(自動承認しない)。
- アップロードされた画像がカード撮影として妥当でない(LABEL_DETECTIONで対象外と判定される、無関係な被写体等)場合、解析を「判断不能」として「要確認」に倒す。
- OCR結果が読み取れない・複数候補があり一意に定まらない場合も「判断不能」として「要確認」に倒す。
- 同一取引に対して複数回の再撮影アップロードが行われた場合、最新の解析結果を有効とし、過去の解析結果は履歴として保持する。
- 出品時・到着後のいずれかの画像が許容サイズや解像度の下限を満たさない場合、解析前にbackendが保存を拒否する。
- 偽造カードであっても、印字内容(カード名・型番)が本物と同一に模されていればOCR突合だけでは検出できない。本MVPは「申告と全く異なるカードが送られていないか」という一次スクリーニングまでを範囲とし、精巧な偽造の検出は対象外(自社の画像比較ロジック側の課題)である。

## Requirements

### Functional Requirements

- **FR-001**: システムは、PSA証明書番号を持たない出品者が出品時にカードの四隅等の画像を複数枚アップロードできなければならない。
- **FR-002**: システムは、アップロードされた画像をCloud Storageの非公開バケットへ保存し、DBにはobject key・content type・byte size・SHA-256・撮影種別(出品時/到着後)・作成者・対象の出品/取引のみを記録し、画像本体をDBへ保存してはならない。
- **FR-003**: システムは、商品到着後に購入者が同一箇所の再撮影画像をアップロードできなければならない。
- **FR-004**: システムは、Vision APIのOCR(TEXT_DETECTION)・オブジェクト位置検出(OBJECT_LOCALIZATION)・ラベル検出(LABEL_DETECTION)を用いて、到着後画像を解析しなければならない。
- **FR-005**: システムは、Vision APIのOCR結果が出品時に申告されたカード名・型番等の内容と整合するかどうかを`内容整合`または`要確認`のいずれかに正規化しなければならない。
- **FR-006**: システムは、Vision APIの解析結果単独では真贋・個体の同一性を確定してはならず、内容不一致・解析エラー・判断不能はすべて`要確認`に倒さなければならない。
- **FR-007**: システムは、Vision APIおよびCloud Storageへの署名付きURL発行を含む外部API呼び出しをbackendからのみ行い、認証情報をブラウザへ渡してはならない。
- **FR-008**: frontendはbackendのAPIを直接呼び出さなければならず、同等のロジックを重複させるServer ActionやNext.js API Routeを追加してはならない。
- **FR-009**: システムは、`要確認`となった解析結果を運営者が一覧・詳細で確認できるようにしなければならない。
- **FR-010**: UIは、内容チェックの結果が現物の真正性・個体の同一性を保証するものではない旨(精巧な偽造品は検出できない旨を含む)を利用者に表示しなければならない。
- **FR-011**: システムは、氏名・住所等の個人情報とカード画像・解析結果を分離して扱い、真贋チェックに不要なPIIを保存してはならない。
- **FR-012**: システムは、出品時画像と到着後画像が物理的に同一個体であることの照合(画像ハッシュ・特徴点比較等)を行ってはならない。これは本MVPの対象外とし、別タスクで扱う。

### Key Entities

- **CardImage**: 出品時または到着後にアップロードされたカード撮影画像。object key、content type、byte size、SHA-256、撮影種別(出品時/到着後)、撮影者(出品者/購入者)、対象の出品・取引への参照を持つ。画像本体はCloud Storageに存在し、DBには参照とメタデータのみを保持する。
- **CardImageAnalysis**: 到着後画像に対するVision API解析・内容整合性チェックの実行結果。対象画像への参照、突合対象とした出品時申告内容(カード名・型番等)、実行状態(処理中/完了/失敗)、正規化結果(`内容整合`/`要確認`)、Vision APIの解析要約(OCRテキスト・検出ラベル)、実行時刻を持つ。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 出品者は出品フロー内で四隅等の画像アップロードを追加の離脱なく完了できる。
- **SC-002**: 購入者が到着後の再撮影画像をアップロードしてから、内容チェック結果(`内容整合`/`要確認`)が数十秒〜数分以内に表示される。
- **SC-003**: 低品質画像・申告内容との不一致・突合対象欠落・Vision API障害・判断不能のいずれのケースでも、100%が`要確認`に正規化され、自動で`内容整合`とされることがない。
- **SC-004**: 運営者は`要確認`となった全件を、出品時申告内容・対象画像・解析要約付きで漏れなく確認できる。

## Assumptions

- 本機能はPSAなし経路(docs/design/system-architecture.md §5.3.2)のみを対象とし、PSA証明書照会経路(#15で実装済み)は対象外とする。
- Gemini APIによる補助説明生成・属性抽出(docs/design/api-catalog.md §5.4)は本MVPのスコープ外とし、将来の拡張として扱う。
- **物理的な同一個体照合(いわゆる「自社の画像比較ロジック」)は本MVPの対象外とする。** Cloud Vision APIはOCR・ラベル・領域検出のみを提供し、2枚の画像が同一の物理カードであることを保証しない(docs/design/api-catalog.md §5.3)。個体識別には画像ハッシュ・特徴点比較(OpenCV等)・専用の類似度モデルが別途必要であり、精度検証を要する重い課題のため別タスクとして切り出す。本MVPでは「出品時申告内容とVision APIのOCR結果が食い違っていないか」という内容レベルの一次スクリーニングまでを提供し、精巧な偽造品(印字内容が本物と同一)の検出はできないことをUIで利用者に明示する(FR-010)。
- カード画像は取引成立から一定期間(発送・到着・紛争対応に必要な範囲)保持し、それ以降の保持方針は本仕様のスコープ外とする。
- 決済・発送そのものの状態管理は別機能(出品・取引管理)に依存し、本機能は「出品時画像あり」「到着後画像あり」という2つの撮影イベントの存在を前提とする。
- Vision APIの呼び出し量・レート制限・課金上限は、PSA APIと同様に契約条件確認後に運用上のquotaとして別途定める(docs/design/system-architecture.md §9相当の未決定事項)。
