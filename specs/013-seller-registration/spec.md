# Feature Specification: 販売者登録フロー実装

**Feature Branch**: `feat/13-seller-registration`

**Created**: 2026-08-17

**Status**: Draft

**Input**: User description: "GitHub Issue #13「販売者登録フロー実装」。poc/ekyc/で検証済みの表示名登録〜eKYC(Didit)本人確認〜webhook/pollingによる状態確認フローを、backend(Hono/PostgreSQL)とfrontend(Next.js)へ移植する。運営者による審査中(in_review)の承認・却下確定は、既存DBスキーマがoperator sourceを既にサポートしており追加コストが小さいため、最小実装としてスコープに含める。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 表示名で販売者登録する (Priority: P1)

販売者になりたいユーザーは、表示名を入力するだけでTrustcaの販売者アカウントを作成できる。

**Why this priority**: これがなければ本人確認(eKYC)を開始できず、それ以降の全フローが成立しない、最初の入口となる操作である。

**Independent Test**: 表示名を送信し、販売者アカウントが作成され、本人確認前の状態(`pending_kyc`)であることを確認する。

**Acceptance Scenarios**:

1. **Given** 未登録のユーザー、**When** 有効な表示名(1〜100文字、空白のみは不可)で登録する、**Then** 販売者アカウントが作成され、審査状態が「本人確認待ち」になる。
2. **Given** 未登録のユーザー、**When** 空文字または100文字を超える表示名で登録する、**Then** 登録は拒否され、理由を含むエラーが返る。
3. **Given** 登録済みの販売者、**When** その販売者の公開情報を取得する、**Then** 表示名と現在の審査状態が、本人確認のPIIを含まない形で返る。

---

### User Story 2 - 本人確認(eKYC)を開始する (Priority: P1)

登録済みの販売者は、本人確認セッションを開始し、外部本人確認サービスのホスト画面へ進める。

**Why this priority**: 本人確認を経なければ販売者として承認されず、Trustcaの「出品前の事前審査」という差別化価値が成立しない。

**Independent Test**: 販売者IDで本人確認セッション作成を要求し、遷移先URLが返り、その販売者の進行中セッションが1件作成されることを確認する。

**Acceptance Scenarios**:

1. **Given** 本人確認待ちの販売者、**When** 本人確認の開始を要求する、**Then** 外部サービスのセッションが作成され、遷移先URLが返る。
2. **Given** 既に進行中の本人確認セッションを持つ販売者、**When** 再度開始を要求する、**Then** 新規セッションを重複作成せず、既存の進行中セッションの遷移先を返す。
3. **Given** 存在しない販売者IDまたは自分以外の販売者ID、**When** 本人確認の開始を要求する、**Then** 開始できず、エラーが返る。
4. **Given** 過去の本人確認が拒否・中断・期限切れで終了している販売者、**When** 再度本人確認の開始を要求する、**Then** 新しい本人確認セッションを作成できる。

---

### User Story 3 - 本人確認の結果を確認する (Priority: P1)

販売者は、自分の本人確認が「承認」「拒否」「審査中」のいずれであるかを確認できる。

**Why this priority**: 販売者が出品可否を知るための、本フローが提供する最終的な価値。ここが成立して初めて登録〜審査が一巡する。

**Independent Test**: 外部サービスからのwebhook受信、またはポーリングによる状態取得のいずれかを経て、販売者の状態取得が正しい結果を返すことを確認する。

**Acceptance Scenarios**:

1. **Given** 外部サービスが「承認」と判定したセッション、**When** 有効な署名付きの通知を受信する、**Then** 状態が「承認済み」に更新され、出品可能と判定される。
2. **Given** 外部サービスが「否認」と判定したセッション、**When** 有効な署名付きの通知を受信する、**Then** 状態が「否認」に更新され、販売者は再度本人確認をやり直せる状態で表示される。
3. **Given** 外部サービスが人手審査中、または未知の判定を返したセッション、**When** 通知またはポーリングで結果を取得する、**Then** 状態は「審査中」となり、自動的に承認されない。
4. **Given** 署名が無効な通知、**When** それを受信する、**Then** 状態は更新されず拒否し、受信したこと自体は監査目的で記録される。
5. **Given** 既に処理済みの通知と同一のイベント、**When** それが再送される、**Then** 状態は重複更新されない。
6. **Given** ブラウザが本人確認完了後の遷移先(callback画面)を開いた直後、**When** 販売者がその画面を見る、**Then** ブラウザの遷移結果ではなく、サーバー間通信で確認済みの状態だけが表示される。
7. **Given** 進行中の本人確認セッション、**When** 通知が届く前に販売者が状態確認画面を開く、**Then** ポーリングによって最新状態を取得できる。

---

### User Story 4 - 運営者が審査中の判定を確定する (Priority: P2)

運営者は、「審査中」のまま止まっている本人確認について、内容を確認したうえで承認または却下を確定できる。

**Why this priority**: 未知ステータスを自動承認しない設計原則を貫くと、外部サービスが判定できないケースは必ず「審査中」に落ちる。この解消手段がなければ、該当する販売者は永久に出品できないまま止まってしまう。US1〜3(P1)が成立して初めて意味を持つ機能のため、P2とする。

**Independent Test**: 「審査中」の本人確認セッションに対し、運営者が承認または却下を送信し、状態が確定し、その判断が履歴に記録されることを確認する。

**Acceptance Scenarios**:

1. **Given** 「審査中」の本人確認セッション、**When** 運営者が理由を添えて承認を確定する、**Then** 状態は「承認済み」になり、運営者による判断として履歴に記録される。
2. **Given** 「審査中」の本人確認セッション、**When** 運営者が理由を添えて却下を確定する、**Then** 状態は「否認」になり、運営者による判断として履歴に記録される。
3. **Given** 既に「承認済み」または「否認」で確定している本人確認セッション、**When** 運営者がその判定を上書きしようとする、**Then** 上書きは拒否される(対象は「審査中」由来のケースに限定)。
4. **Given** 運営者としての権限を持たない呼び出し元、**When** 承認・却下の確定を試みる、**Then** 操作は拒否される。
5. **Given** 「審査中」のセッションを確認したい運営者、**When** 一覧を取得する、**Then** 現在「審査中」であるセッションと、その判定根拠(チェック結果・状態履歴)を確認できる。

---

### Edge Cases

- 外部本人確認サービスの結果取得がタイムアウト・一時エラーを返した場合、状態を書き換えずに現在の状態を維持し、次回の通知またはポーリングで再試行する。
- 通知のタイムスタンプが許容範囲を大きく外れている場合、署名形式が正しくても無効な通知として扱う。
- 既に「承認済み」または「否認」で確定した本人確認に対し、古い(確定前の)通知が後から届いた場合、確定済みの状態を上書きしない。
- 同一の販売者に対して、進行中(未確定)の本人確認セッションは常に1件までとし、確定前に新規セッションを重複して作成できない。
- 運営者が確定した判断は、外部本人確認サービス側の元の判定を書き換えるのではなく別記録として残し、「外部サービスが何と言ったか」と「運営者が何を判断したか」の両方を後から追跡できるようにする。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、表示名(1〜100文字、空白のみは不可)でユーザーと販売者プロフィールを作成できなければならない。
- **FR-002**: システムは、新規登録された販売者の審査状態を「本人確認待ち」で初期化しなければならない。
- **FR-003**: システムは、販売者の公開情報(表示名・現在の審査状態など、本人確認のPIIを含まない項目)を取得できなければならない。
- **FR-004**: システムは、販売者ごとに本人確認セッションを開始でき、外部本人確認サービスのホスト画面への遷移先を返さなければならない。
- **FR-005**: システムは、同一販売者について、未確定(開始前・進行中・審査中)の本人確認セッションが複数同時に存在することを防がなければならない。
- **FR-006**: システムは、外部本人確認サービスからの状態変更通知を受信し、送信元を検証(署名検証)しなければならない。
- **FR-007**: システムは、検証に失敗した通知を拒否し、その場合は本人確認状態を更新してはならない。
- **FR-008**: システムは、有効な通知の再送を検知し、同一イベントによる状態の重複更新を防がなければならない。
- **FR-009**: システムは、外部サービスの未知または未対応の判定結果を自動承認せず、「審査中」として扱わなければならない。
- **FR-010**: システムは、本人確認状態が変化するたびに、変更前後の状態を含む履歴を追記しなければならない。
- **FR-011**: システムは、進行中の本人確認セッションについて、通知が届かない場合でも販売者からの問い合わせ(ポーリング)によって最新状態を取得できなければならない。
- **FR-012**: システムは、氏名・住所・生年月日・身分証番号・身分証および顔画像等の本人確認PIIを保存してはならない。
- **FR-013**: システムは、外部本人確認サービスの秘密情報(APIキー・署名検証鍵)をサーバー側だけで扱い、ブラウザやログへ露出してはならない。
- **FR-014**: 販売者は、「承認済み」「否認」「審査中」のいずれの状態も、自分の登録に対して確認できなければならない。
- **FR-015**: システムは、「承認済み」の本人確認結果を持つ販売者だけを「出品可能」と判定しなければならない(審査中・否認・未知の判定では出品不可)。
- **FR-016**: システムは、「審査中」の本人確認セッションの一覧と、その判定根拠(チェック結果・状態履歴)を運営者が確認できなければならない。
- **FR-017**: システムは、運営者による承認・却下の確定を受け付け、対象を「審査中」由来の本人確認セッションに限定しなければならない(既に確定済みの承認・否認は上書きできない)。
- **FR-018**: システムは、運営者の確定操作を、運営者としての権限を持たない呼び出し元から拒否しなければならない。
- **FR-019**: システムは、運営者による判断を行った場合も、外部本人確認サービスの元の判定を上書きせず、変更前後の状態・判断理由・判断主体を履歴に残さなければならない。

### Key Entities

- **販売者(Seller)**: 表示名と、販売者としての審査状態(本人確認待ち・審査中・承認済み・否認・停止)を持つアカウント。購入者を含む共通アカウントに販売者としての属性が付与されたもの。
- **本人確認セッション(Verification)**: 外部本人確認サービスのセッションに対応し、正規化された状態(未開始・進行中・審査中・承認済み・否認・中断・期限切れ)とチェック結果(本人確認書類・生体照合・顔照合等の合否)を保持する。販売者ごとに未確定のセッションは1件まで。
- **本人確認イベント(Verification Event)**: 状態変化を記録する追記型の履歴(いつ・どの状態からどの状態へ・誰(外部サービス/運営者)の何をきっかけに変化したか)。
- **通知イベント(Webhook Event)**: 外部サービスからの状態変更通知の受信記録。署名の有効性と、再送検知に使う識別子を保持する。
- **運営者(Operator)**: 「審査中」のセッションを確認し、承認・却下を確定できる権限を持つ主体。本機能では一般利用者と同じアカウント体系を前提とせず、限定された認可方式で識別される想定。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 販売者は、表示名を送信してから本人確認セッションの遷移先URLを受け取るまでを60秒以内に完了できる。
- **SC-002**: 有効な状態変更通知を受信してから、販売者向けの状態表示(承認済み/否認/審査中)に最新結果が反映されるまで数秒以内で完了する。
- **SC-003**: 未知の外部判定・タイムアウト・不正な署名を含む異常系のテストケースで、意図せず「承認済み」と表示されるケースが0件である。
- **SC-004**: 同一の状態変更通知を複数回受信しても、本人確認状態の履歴に重複した変更が記録されない。
- **SC-005**: 本人確認完了後にブラウザが遷移先画面を開いても、その遷移結果だけをもとに「承認済み」と表示されることはない(サーバー側で確認済みの状態だけが表示に使われる)。
- **SC-006**: 本人確認PII(氏名・住所・生年月日・身分証番号・画像等)が、本機能のいかなる保存先にも記録されていないことを確認できる。
- **SC-007**: 解消手段がなく「審査中」のまま止まっている販売者が0件である(すべての「審査中」セッションを運営者が確認・確定できる)。

## Assumptions

- 本機能は`poc/ekyc/`で検証済みの表示名登録〜eKYC本人確認〜状態確認フローを踏襲し、対象となる外部本人確認サービスは既に契約・利用可能である前提とする。
- 本機能は、`backend/src/db/migrations/0001_initial_schema.sql`で既に作成済みのテーブル(販売者アカウント、審査状態、本人確認セッション、状態履歴、通知受信履歴)をそのまま利用し、スキーマ変更は行わない。`verification_events`/`seller_verifications`の`source`列は既に`operator`を許可しているため、運営者判断の追加に伴うスキーマ変更は不要である。
- 本人確認の開始・詳細な状態取得を「本人」だけに許可する認可の具体的な方式(既存のウォレット署名ログインとの統合方法など)は、本仕様では確定させず、実装計画の段階で具体化する。MVPとしては、販売者IDを知っている呼び出し元が操作できる最小限の認可から始めてもよい。
- 運営者向けの認可は、本番相当のRBACではなく、共有シークレットやBasic認証程度の簡易な方式で足りるものとする(ブラウザから誰でも叩けないことだけを担保する)。専用の運営者アカウント管理は本機能の対象外とする。
- 承認後の出品数・金額上限などの条件付き制限(seller_limits)の運用ロジックは、本機能の対象外とし、別Issueで扱う。
- フロントエンドの画面URL構成やコンポーネント分割の詳細は本仕様では確定させず、実装計画の段階で具体化する。最低限、登録フォーム・本人確認開始操作・状態表示・運営者向けの審査中一覧と確定操作が、それぞれ辿れることを前提とする。
